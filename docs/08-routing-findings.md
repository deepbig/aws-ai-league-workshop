# 08. 라우팅 하위문제 분석 (Navigator Tool 설계 근거)

> ⚠️ 이 문서는 **에이전트 설계의 한 하위 결정**을 데이터로 뒷받침하는 부속 자료다.
> 워크샵의 본체 = LLM 에이전트 설계·반복개선 → **[docs/09-agent-design.md](09-agent-design.md)** 가 중심.
>
> 여기서 얻는 결론은 단 하나: **"경로는 LLM이 추측하지 말고 결정론적 navigate Tool에 위임하라"**
> (LLM 경로추정은 부정확, 검증된 알고리즘은 진짜 최적의 99.8~100%).
> 이 알고리즘은 [agent/tools.md](../agent/tools.md)의 `navigate` Lambda 구현으로 편입된다.

---

## 1. 문제를 무엇으로 환원했나

게임 = 시작점에서 제한 시간 안에 보상 노드(코인=가치, 챌린지=격파점수, 보물=보너스)를
방문해 점수 합 최대화. **챌린지를 코드로 풀면 정답률 100%·생명 손실 0** →
생명 제약이 사실상 사라지고 문제는 순수 **Orienteering(예산제약 prize-collecting 경로)**.

- 비용 모델: `cur→nid` = 최단거리(BFS) + 노드 solve_cost(코인 0, 챌린지 = solve_cost_steps)
- 점수: 시간 예산 내 방문 노드 value 합
- → 핵심 의사결정 = **"어떤 보상을, 어떤 순서로 방문할까"**

## 2. 측정 방법 (정직한 검증)

- `sim/planners.py`: 점진적으로 강한 플래너 7종.
- `sim/bench.py`: 3단계.
  - **SMALL(N~11)·MID(N~18)**: **Held-Karp 비트마스크 DP로 진짜 최적해**를 계산해
    각 플래너의 `%opt`(최적 대비 비율) 측정. ← 핵심 신뢰 근거
  - **FULL(N~28)**: 최적 계산 불가 → 장기 ILS를 레퍼런스로 상대 비교 + 절대점수.
- 모든 맵은 시작점 연결성 보장(고립 seed 제거)으로 공정 비교.

## 3. 플래너 (약→강)

| 플래너 | 알고리즘 | 비고 |
|---|---|---|
| nearest | 최근접 노드 반복 | 베이스라인 |
| greedy | 가치/비용비 탐욕 | 베이스라인+ |
| **greedy+LS** | 탐욕 + 2-opt + or-opt + 미방문 삽입 | **빠른 실전용** |
| GRASP | 무작위화 탐욕 다중재시작 + LS | 강 |
| ILS | LS + double-bridge 교란 반복 | **최강급** |
| SA | 시뮬레이티드 어닐링 + 정체 시 LS 강화 | 강 |
| **BEST(앙상블)** | greedy+LS·GRASP·ILS·SA 중 최고 채택 | **배포 권장(최고점)** |

## 4. 확정 실측 — 진짜 최적해(Held-Karp) 대비

`python3 sim/bench.py` 재현 가능. N≤18은 **Held-Karp DP로 계산한 진짜 최적해 대비** %.

| 규모 | 레퍼런스 | nearest | **greedy+LS** | **ILS** |
|---|---|---|---|---|
| SMALL N~11 | 진짜 최적해 | 98.36% | **99.86%** | **100.00%** |
| MID N~16 | 진짜 최적해 | 93.46% | **99.78%** | **99.87%** |
| FULL N~28 | 장기 ILS(계산상한 초과) | 88.01% | 96.18% | **99.64%** |

절대점수(FULL, 20 seed): `nearest 6629 → greedy+LS 7244 → ILS 7504`.
개발 초기 단순 그리디 대비 **약 +17%**.

**해석**:
- ILS는 측정 가능한 모든 규모에서 **진짜 최적해의 99.87~100%** → 최적에 도달/근접.
- greedy+LS는 **~99.8% 최적이면서 15ms급** → 실시간 in-agent용 최선.
- 추가 라우팅 개선 여지 = 진짜 최적 대비 **0.2% 미만** → **라우팅은 사실상 해결**.
  (FULL의 ILS 99.64%는 반복횟수 차이일 뿐, 반복을 늘리면 레퍼런스에 수렴)

> 남은 점수 레버는 *알고리즘이 아니라 당일 규칙*(보너스 조건·배점·페널티)뿐.
> → `sim/config.json`을 [확정]값으로 교체 후 재실행으로 흡수(구조는 불변).

## 5. 결론 — "가장 높이는 방법"

1. **챌린지는 전부 코드로 푼다** (Code Interpreter/Lambda). 정답률 100%, 생명 손실 0.
   라우터가 챌린지를 100% 가치 노드로 취급할 수 있게 되는 전제.
2. **경로는 강한 Orienteering 솔버로** 짠다:
   - **실전 in-agent Navigator**: `greedy+LS` — 15ms 수준, 작은 규모에서 ~99.8% 최적.
     매 턴 재계획해도 부담 없음(receding horizon).
   - **초기/여유 시 정밀화**: `ILS`(또는 BEST 앙상블) — N≤18에서 최적의 99.8~100%.
     게임 시작 시 1회 또는 시간 여유 구간에서 경로를 정밀 최적화.
3. **추가 점수 한계는 ~0.2%**: ILS가 이미 진짜 최적의 99.8%+. 더 복잡한 솔버를 더해도
   기대 이득 < 0.2% → **여기서 라우팅은 사실상 해결**. 남은 점수 레버는 *당일 규칙*
   (보너스 조건·배점)뿐 → `config.json` 갱신 후 재시뮬레이션으로 흡수.

## 6. 워크샵 적용 매핑

| 시뮬레이터 | 실제 AgentCore 구현 |
|---|---|
| `plan_greedy_ls` / `plan_ils` | Navigator Sub-Agent의 Lambda 경로 알고리즘 |
| Held-Karp `plan_exact` | 소규모 구간 최적 경로 검산용(선택) |
| 챌린지 = 가치 노드 | Challenge Solver가 Code Interpreter로 100% 정답 |
| `config.json` | 당일 "극대화하는 방법/보너스/배점"으로 교체 |

→ Navigator는 LLM 추정 금지, **결정론적 알고리즘(greedy+LS, 여유 시 ILS)** 고정.
실행 절차/프롬프트는 [docs/06-winning-strategy.md](06-winning-strategy.md).
